How Mirage Tests One API: Stateful Exploration,
Runtime Evidence, and Conditional Oracles
Mirage Project
Technical report on roadmaps 008–010
Repository evidence review, November 15, 2026
Abstract—Mirage tests a deep-learning API by placing its
actual execution inside generated training programs, explor-
ing tensor representations and training-state transitions, and
checking conditional metamorphic relations at aligned semantic
checkpoints. The main challenge is establishing a chain from
a proposed state to a valid execution and an applicable cor-
rectness judgment. This report explains the complete single-
API testing procedure, including source/follow-up construction,
target-backward evidence, repair, coverage feedback, and a
recorded optimizer-update example. It compares the methods
and metrics of roadmaps 008–010 using existing frozen protocols
and saved results, with no new framework experiments. The
evidence shows three distinct outcomes: relational exploration
in 008 reduced valid yield, 009 improved some observed joint
coverage while planned exploration regressed, and 010 attained
ten of ten planned gradient-layout/update goals while losing
numerical-audit agreement and ordinary coverage. These single-
seed studies establish bounded capabilities and tradeoffs; they
do not establish general bug-ﬁnding superiority or exhaustive
training-state coverage.
Index Terms—deep-learning framework testing, stateful test-
ing, tensor representation, metamorphic testing, autograd, opti-
mizer state
I. PURPOSE AND MAIN TAKEAWAY
Given one API, Mirage searches for executed combinations
of tensor representation and training state. A test is more than
a generated API call: it includes an execution conﬁguration,
evidence that the intended target and required backward path
ran, a checkpoint-speciﬁc state obligation, and an oracle whose
assumptions have been established. A successful process exit
alone provides none of these conclusions.
The project architecture separates a state-transition sampler
and MR selector, a training-program generator, and an inspec-
tor/correctness oracle. The implemented stateful path realizes
these responsibilities through a corpus-guided controller, gen-
erated build/run programs, runtime probes and hooks, and
conditional pair evaluation. The generator creates programs
and proposes transitions; the framework establishes evidence
and decides what can be compared.
This report makes three contributions to understanding the
implementation:
• An operational account of how one API moves through
generation, state planning, execution, oracle assessment,
and exploration feedback.
• A precise distinction between operand joint coverage,
qualiﬁed backward-linked joint coverage, and the opti-
mizer update chain introduced in roadmap 010.
• A source-linked comparison of roadmaps 008–010 that
retains negative results, missing measurements, oracle
limitations, and incompatible experimental populations.
a) Scope and historical boundary.: The methods and re-
sults here concern the frozen 008–010 engines and the formal
campaigns referenced by their roadmaps [1], [2], [3]. The
current working tree also contains roadmap 011 changes. Its
framework-owned input-representation traversal and revised
local-oracle admission are outside this comparison. Likewise,
roadmap 009’s postformal oracle correction and roadmap
010’s later single-arm slogdet follow-up are kept separate
from the frozen formal comparisons. This is a software testing
report; it makes no security-evaluation claim.

A. Program, State, and Execution Case

B. Conditional Correctness
For MR M , output comparison is enabled only if
Valid(ea) ∧ Valid(eb) ∧ Aligned(qa, qb)
∧ PreM (ea, eb) ∧ InM (ea, eb). (3)
Then the oracle evaluates OutM (ObsM (ea), ObsM (eb)). Pre-
conditions concern such facts as reviewed source effects,
operator/domain eligibility, and proven target paths. The input
relation constrains initial values, program semantics, environ-
ment, and permitted changes. The output relation speciﬁes
only the observables justiﬁed by that MR. Merely using the
same seed does not establish the input relation.
Four principal verdicts follow. Invalid means a required exe-
cution/path/state obligation failed. Inapplicable means the MR
assumptions or checkpoint alignment were not established.
Pass means an applicable output relation held. Suspected
failure means an applicable relation was violated. A compar-
ison can also remain unassessed when evidence or numerical
conditions are unresolved. An inapplicable but source-valid
case can contribute veriﬁed coverage without receiving a
correctness pass. A source can be valid even when its follow-
up is unusable; source coverage and pair applicability therefore
have different denominators.
III. THE SINGLE-API TESTING PROCEDURE
A. Resolve the Target and Establish a Legal Parent
The controller obtains the installed API signature/docu-
mentation and target device, then asks the LLM for a small
legal program. The stateful contract uses build(device,
seed) to register named inputs, trainable parameters, and an
optional optimizer, followed by run(ctx, probe) to ex-
press execution order. Target observation uses probe.call
for ordinary calls and the relevant supported context/fac-
tory adapters for other target kinds. This differs from
the older canonical training-loop contract, which exposes
forward(ctx) and loss(output). The report’s walk-
through uses the stateful contract actually exercised by the
formal campaigns.
Static checks validate syntax, function signatures, regis-
tration contracts, and permitted program structure. They do
not establish target execution. The worker then executes a
fresh source, captures initialization and runtime evidence, and
checks that the target and required path ran. In backward-
required cases, a loss calling backward() somewhere is
insufﬁcient: evidence must link the relevant target computation
to completed backward. Composite or unobserved edges can
remain unresolved despite real execution.
The path policy matters. The 008 and 009 panels use mixed
policies and contain valid forward-only/context cases; 010
deliberately requires backward for its differentiable six-API
panel. A forward-only case is not retrospectively credited with
target-backward coverage.
B. Choose a Search Opportunity and a Target State
After parent admission, the controller allocates opportunities
among fresh generation, local mutation, and state plans. The
feedback sampler uses smoothed estimates of validity, novelty
and measured cost, with a uniform exploration component.
In the frozen 010 sampler, a candidate’s heuristic score is
proportional to
ˆpvalid ˆgnovelty/ˆt, (4)
and selection mixes normalized scores with uniform prob-
ability. These quantities are search heuristics, not unbiased
statistical estimators. Family-level history can transfer to new
parents while exact goals retain local history.
The bounded goal catalog is built from actual parent ob-
servations. Roadmap 008 adds same-call tensor relations and
selected-axis predicates, retaining at most three conjunctive
goals per plan. Roadmap 009 separates training-state, unary
tensor-state, and tensor-relation proposal opportunities; its
structured response distinguishes planned from unresolved
goals and reports examined IDs. Roadmap 010 adds a library
of known conﬁguration transitions for already veriﬁed opti-
mizer parents. Being offered, examined, proposed, selected,
dispatched, and attained are separate events.
C. Generate or Conﬁgure the Child
A selected plan identiﬁes actions, target predicates and
checkpoints, and injection regions. In the LLM route, the
generator edits the parent program while preserving the MR-
required semantic inputs and initialization. Operand-binding
hints relate selectors to bounded AST expressions and last as-
signments. Unsupported dynamic binding remains unresolved.
The generated edit still needs runtime validation; an expression
hint is not an operand witness.
In 010’s conﬁguration-only route, the library can reuse a
veriﬁed source and request an exact-value-preserving gradient
action at the optimizer boundary. This avoids regenerating
identical computation. The library does not claim the new state
has already been reached. Source obligations remain attached
to the source; follow-up success cannot satisfy them on its
behalf.
Budget admission precedes dispatch. For a known con-
ﬁguration branch, the candidate can use the same par-
ent’s measured completed-worker time, retaining reserve
max(10, 1.5tparent + 5) seconds. Missing/invalid timing falls
back to the ordinary reserve. Fresh quotas and the general
execution deadline remain relevant. A planning opportunity
can fail to run because of budget admission before any LLM
planning request occurs.
D. Execute and Verify Reachability
The worker records actual API operands, outputs, metadata,
events and checkpoints. Call-entry metadata includes bounded

shape/stride, storage grouping/offset and representation prop-
erties. Hooks distinguish output gradients, actual target back-
ward Nodes and attributable operand-gradient events. The
inspector joins witnesses within the same call and checkpoint;
it never assembles a purported joint state from unrelated calls
or times.
Each predicate is checked against the relevant observation.
Missing metadata yields unknown evidence rather than in-
ferred independence or reachability. Shared storage establishes
an allocation relationship, not overlap of occupied tensor co-
ordinates. Operand metadata at forward entry plus a backward
event does not prove that the same representation was saved
or consumed during backward; ordinary v2 coverage explicitly
leaves that claim unsupported.
When a generated program or transition is rejected, feed-
back identiﬁes the blocking stage and expected/observed obli-
gations. Roadmap 009 avoids worker dispatch for identical or
AST-equivalent rejected repairs, and stops state repairs that
fail to improve selected obligations after the permitted repair
step. Such stopping is a budget tradeoff, not a proof that a state
is unreachable. Unresolved runtime exceptions remain distinct
from inspector-conﬁrmed contract violations.
E. Construct and Assess the Follow-up
For an eligible source, the worker selects a supported condi-
tional relation and constructs its follow-up. For representation
testing, this can materialize or transform actual operands
under the backend’s capability/effect constraints. For 010’s
optimizer relation, it changes the selected gradient representa-
tion at the native pre-update boundary. Target/backward/update
obligations survive the transformation; only MR-permitted
representation-speciﬁc follow-up predicates are removed or
adjusted.
The ordinary representation pair observes target outputs and
relevant ﬁnal parameter/input gradients. Writable operations
use a narrower materialized-value effect relation when its
write-role obligations are established. The optimizer pair ob-
serves post-update parameters and optimizer slots. The imple-
mentation does not universally compare every loss, parameter,
optimizer, scheduler and AMP value for every relation.
The frozen backend’s dtype_scaled_v1 screen checks
matching structure, shape and dtype, ﬁnite tensors, and a nor-
malized maximum difference. With s = max(∥A∥∞, ∥B∥∞),
its tensor criterion is
∥A/s − B/s∥∞ ≤ min(0.01, 64ϵdtype), (5)
with zero error when s = 0. Discrete values use exact
comparison; nonﬁnite or unsupported conditions can remain
uncertain. Exact comparison is also retained for the optimizer
outputs as a diagnostic. This policy is a bounded numerical
screen whose applicability requires prior domain checks, not
a universal ﬂoating-point equivalence theorem.
Local numerical-gradient audits are separate from MR
evaluation. They require their own eligible source effects,
target reconstruction/bindings, numerical-domain and stability
evidence, and available budget. Statuses include agreement,

Requests, responses, source/conﬁguration, inspection, ver-

C. What This Example Does and Does Not Test
The example tests whether native SGD consumes equal
logical gradients consistently across their permitted memory
representations. It does not show backward writing into a
noncontiguous accumulation buffer. It also does not explore
an input layout change at torch.add: its transformed ob-
ject is parameter.grad. Finally, all generated momentum
values are zero, so matching empty slot dictionaries does not
demonstrate autonomous nonempty momentum-slot coverage.
Positive-momentum native controls validate a supported com-
parison capability separately from search attainment.
V. HOW THE METHODS EVOLVED
A. Roadmap 008: Bounded Joint Tensor-State Exploration
Roadmap 008 extends unary representation predicates with
selected-axis extent ordering, zero/singleton stride properties,
shared storage and their conjunctions [1]. Candidate witnesses
must belong to the same actual call. Automatic observation is
bounded to four operands in typed-path order and ﬁrst/last
axes, with omitted or unknown measurements recorded. Ex-
plicit predicates can select additional axes without implying
the automatic coverage observer explores them all.
The planner vocabulary is bounded to 29 goals and
at most three conjunctive predicates per plan. The imple-
mentation connects planning, generation, runtime evidence,
joint signatures, corpus admission and reporting. It intro-
duces state-semantic-2 and rejects mixed/legacy active-
corpus versions instead of silently migrating their coverage.
The original baseline and new engine are therefore scored
with one frozen v2 observer; native v1 versus v2 totals cannot
measure improvement.
The ﬁnal candidate requests 41 tensor-relation goals and
attains nine; only two also support an applicable MR. The
broader axis-or-relation population is 73 requested, 15 at-
tained and three MR-applicable. The 58 unsuccessful broader
attempts include 32 state-attainment failures, 25 unresolved
runtime failures and one static-contract failure. These include
repair retries, not independent samples. More expressible goals
did not produce greater valid search yield.
B. Roadmap 009: Evidence-Guided General State Exploration
Roadmap 009 addresses losses exposed by 008: imbalanced
proposal supply, operand-selector/source mismatches, nonac-
tionable plans, ineffective repairs, source-effect certiﬁcates and
excessively fragmented feedback [2]. It introduces family-
level planning opportunities, structured planned/unresolved
responses with examined IDs, bounded AST binding hints,

targeted unmet-predicate diagnostics, early duplicate-repair re-
jection and family-shared cost/validity priors. Prompt coverage
summaries reserve bounded representatives for both unary and
joint evidence.
The formal reference receives the same corrected source cer-
tiﬁcate and public API resolver as the candidate. Thus the ﬁnal
contrast concerns a bundle of exploration/generation/controller
changes, not the certiﬁcate correction alone. The postformal
local numerical certiﬁcate correction is not part of these frozen
formal results.
The additional qualiﬁed joint metric requires original source
validity, a source program certiﬁcate, a required and observed
backward path, and an operand-gradient contribution on at
least one side of the joint witness. It does not require both sides
and does not mean a planned memory–training conjunction
was reached. All 54 candidate qualiﬁed joint units come from
fresh cases. In the formal search, planned-valid cases decrease
from 29 to 17, memory-goal-valid cases from 19 to two, and
explicit memory–training goal attempts remain zero in both
arms. Training-family attainment rises from 7/16 to 15/38, but
the report attributes the added attainments to forward-only
boundary/context counts; true backward-lifecycle successes
remain two in each arm. Aggregate observed coverage must
not conceal this missing planned interaction evidence.
C. Roadmap 010: Gradient Representation and Real Updates
Roadmap 010 connects a speciﬁc gradient representation
to attributable target backward and a completed native op-
timizer update [3]. Its initial admitted domain is dense real
CPU ﬂoat64, exact-type native SGD, cold state, one update,
ﬁnite positive scalar learning rate, momentum in [0, 1), zero
weight decay/dampening, disabled Nesterov/maximize/fore-
ach/fused/differentiable modes, and no closure, AMP, sched-
uler, capture, compilation or foreign hooks.
Stable registered parameter identities and group order re-
place transient slot indices. Runtime evidence must connect
the same target operand, target Node contribution, completed
backward, parameter post-accumulate event, and consumed
gradient, including object/version/value evidence. A zero VJP
or zero parameter change does not invalidate an otherwise
proven update; nonzero magnitude is diagnostic rather than
an applicability prerequisite.
The MR checks reviewed native domain/source effects; the
same program, environment, initial state and registry; exact
logical pre-step parameters, gradients and slots; matching
completed semantic step; and the sole permitted gradient-
representation difference. It compares post-update parameter-
s/slots using the existing screening policy and additionally
records exact equality. Its optimizer-chain-1 signatures
are reported separately from ordinary tensor joint units. Nei-
ther is a substitute for the other.
After development exposed budget admission before plan-
ning, the ﬁnal bundled treatment adds the conﬁguration li-
brary and parent-worker reserve described above, plus generic
prompts explaining the already supported straight-line source
fragment. The ﬁnal reference retains the 009 generator/plan-
ner/controller with common 010 runtime, contracts, inspec-
tor and MR overlays. Consequently, zero observed reference
chains are measured zeros under the shared observer. Miss-
ing reference conﬁguration-reuse instrumentation is instead
reported as unmeasured, even where an exporter defaults its
ﬁeld to zero.
VI. METRIC DEFINITIONS AND COMPARABILITY
A. Cases, Applicability, and Goals
Let A denote persisted attempts, including generation/plan-
ning rejections and repair attempts; V original source-valid
cases with preserved obligations; and J applicable MR pairs,
meaning pass or suspected failure. Then
Rvalid = V /A, RMR = J/V. (6)
The second rate is not pass rate over every attempted com-
parison. Its relationship to validity depends on the explicitly
reported source and pair gates. A goal-attainment denominator
is all attempts requesting that goal class, including failed gen-
eration/execution. For an optimizer conjunction, the numerator
also requires the original source-valid linked chain and every
requested companion predicate. Zero requested goals yields an
undeﬁned rate, not 100% success.
B. Coverage Units
API coverage counts APIs with validated execution against a
declared conﬁgured pool; 010 reaches ﬁve of six in both arms.
Unary state-semantic units combine API, operand path, se-
mantic checkpoint, normalized data/representation/state facts,
environment and veriﬁed path relations. Joint units combine
same-call operand witnesses and their measured relation.
Counts are unique observed signatures, not percentages of all
feasible states. The observer’s omission counts constrain their
interpretation.
Transition units identify normalized veriﬁed transition sig-
natures within an API; they are not a proof of comprehen-
sive transition-space exploration. API–MR units count distinct
API/relation pairs with an applicable judgment. State–MR
units attach applicable relations to veriﬁed semantic units.
These are observed combinations; candidate sets are bounded
and feasibility is provisional. An API’s multiple calls or repair
retries are not automatically distinct coverage.
Qualiﬁed joint is 009’s additional ﬁltered operand measure.
Optimizer-chain units are a separate versioned 010 measure
for target-linked consumed gradients and updates. Optimizer
units are not backﬁlled into missing historical observations
and cannot be added to ordinary units to offset a regression.
Source/follow-up and fresh/planned origin are reported sep-
arately. A fresh observation can be useful without being a
planned target achievement.

VII. EXISTING FORMAL RESULTS
A. Protocols and Populations
All three campaigns use exactly one ﬁnal seed (zero)
per arm/API, fresh isolated corpora, balanced or alternating
arm ordering, a shared prepared Qwen3.8-27B BF16/MTP3
model service within each study, and frozen runtime/oracle
comparisons [5], [6], [7]. Recorded environments include
Python 3.14.10, PyTorch 2.15.0+cu132 and NVIDIA H200
allocation hardware. The 008/009 API panels contain CPU
and CUDA targets; 010’s optimizer panel is CPU eager. Shared
model/kernel caches are not fully controlled.
The 008 panel contains ten APIs. The 009 panel adds
six preregistered search-held-out APIs, for 16 total; held-out
means no development search on those APIs, not that imple-
mentation or tests never used them. The 010 panel contains
sin, add, mm, linear, tanh and bmm; only sin/add are
development search targets. Table II speciﬁes budgets and path
policy. Because pools, policies, budgets and capabilities differ,
comparisons are within each phase. None of the ﬁgures is a
longitudinal ranking of three interchangeable versions.
B. 008: Added Capability, Lower Yield
Table III and Fig. 1 show valid sources decreasing from 132
to 94, applicable comparisons from 69 to 57, and common
source joint units from 327 to 167. Despite the lower number
of applicable comparisons, conditional MR applicability rises
because valid cases fall faster. Per-search-second valid yield
decreases from approximately 0.0817 to 0.0599. Neither the
higher conditional rate nor the new goal vocabulary establishes
a better search engine.
One baseline slogdet suspect is autonomously generated
and replayed; the candidate arm has none. Later exact analyt-

VIII. RESEARCH POSITION AND LIMITATIONS
Automatic-differentiation differential testing and numerical-
instability ﬁltering precede Mirage: NablaFuzz treats APIs
as tensor/vector functions and compares outputs/derivatives
across execution scenarios [8]. Operator-constraint exploration
also has precedents: GPU-Fuzz models operator parameter
constraints and uses constraint solving for framework tests [9].
These establish relevant methodological context; this report
makes no ﬁrstness claim for layout variation, gradient testing
or generic API fuzzing. Roadmap 010’s literature review
additionally records native PyTorch precedents for comparing
parameter updates across gradient layouts [3]. The research hy-
pothesis is the integration of state predicates, attributable run-
time evidence, conditional comparisons and coverage-guided
exploration.
The evidence has six practical limits. First, the single
seed and short, different panels preclude conﬁdence intervals,
statistical superiority, and individual-component causal attri-
bution. Repairs, shared source children and paired members
are dependent. Second, bounded observers omit operands/axes
and have no exhaustive feasible-state denominator. Third,
broad architectural dimensions remain partly unimplemented:
warm/multiple optimizer steps, other optimizers, AMP/sched-
uler/distributed interaction and backward-write buffer layouts
require new validated slices.
Fourth, source-effect and direct-edge proofs are conserva-
tive; missing certiﬁcates or composite edges reduce assessment
even for legal programs. Fifth, stronger optimizer coverage
can reduce ordinary program diversity and numerical-audit
eligibility. A budget policy must measure both reached states
and assessable states. Sixth, known-trigger controls, posthoc
diagnosis, replay, minimization and independent corroboration
have different evidential roles. The existing formal studies do
not establish zero false positives, zero false negatives, cross-
framework generalization or absence of bugs.

IX. CONCLUSION
For one API, Mirage builds a bounded search over gen-
erated programs and execution conﬁgurations, veriﬁes the
actual target/path/state, and applies only those conditional
oracles whose evidence is established. Roadmaps 008–010
sharpen different parts of that process: relational tensor wit-
nesses, evidence-guided exploration, and a native consumed-
gradient/update chain. Their results support the optimizer
slice’s operational feasibility while exposing valid-yield,
planned-exploration and oracle-eligibility bottlenecks. The ap-
propriate next question is how many diverse states become
both runtime-veriﬁed and meaningfully assessed within a ﬁxed
budget.
